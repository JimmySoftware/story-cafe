# Runbook ร้าน Story Cafe — เมื่อระบบมีปัญหา

> เขียนสำหรับคนที่ไม่ใช่โปรแกรมเมอร์ ตอนตี 6 ร้านเปิดไม่ได้ · ทำทีละข้อ ไม่ต้องรีบ
> ตัวเลขลิมิตทั้งหมดอ้างจาก `data/free-tier.json` (ตรวจจากเอกสารทางการ 26 ต.ค. 2026) — ถ้าเอกสารเปลี่ยน แก้ที่ไฟล์นั้นที่เดียว
> ข้อที่ติดป้าย **[ตรวจหลังสมัคร]** คือต้องมีบัญชี Supabase Cloud / Cloudflare จริงถึงจะทดสอบได้ ตอนนี้ยังไม่เคยลองกับระบบจริง

## Supabase หลับหรือล่ม

อาการ: เว็บบอกว่าโหลดข้อมูลไม่ได้ / POS ขึ้นว่าออนไลน์ไม่ได้ / แอปเจ้าของไม่มียอดขาย

1. **ขายต่อก่อน ไม่ต้องรอระบบ** — POS ขายต่อได้ด้วยคิว offline (ออฟไลน์): กดขายตามปกติ บิลจะเก็บในเครื่องแล้วส่งขึ้นระบบเองเมื่อ Supabase กลับมา (ดูบท 21) ห้ามล้างข้อมูลเบราว์เซอร์/ถอนการติดตั้งแอป POS ระหว่างที่ยังมีบิลค้างในคิว
2. **เว็บยังโชว์เมนูได้เอง** — เมนูและราคาฝังอยู่ในเว็บ (มาจาก `data/menu.csv`) ส่วนชื่อร้าน เวลาเปิด เบอร์ ใช้ไฟล์สำรอง `web/public/menu-fallback.json` ลูกค้าจะเห็นข้อความว่าแสดงจากไฟล์สำรอง การสั่งล่วงหน้าและร้านออนไลน์จะใช้ไม่ได้จนกว่าระบบกลับมา — แจ้งลูกค้าทาง LINE แทน
3. **ตรวจว่าเป็นที่ระบบหรือที่เน็ตร้าน** — เปิดเว็บอื่นบนเครื่องเดียวกัน ถ้าเน็ตปกติ ให้ดูหน้าสถานะ Supabase (https://status.supabase.com) **[ตรวจหลังสมัคร]**
4. **ถ้าโปรเจกต์ถูก pause** — แผนฟรีอาจ pause โปรเจกต์ที่ไม่ค่อยมีการใช้งานภายใน 7 วัน เข้า Supabase Dashboard → เลือกโปรเจกต์ → กด Restore / Resume แล้วรอจนสถานะเป็น Healthy **[ตรวจหลังสมัคร]** (ไม่ให้ถูก pause: อย่าปล่อยร้านเงียบเกิน 7 วัน เปิดเว็บหรือขายผ่าน POS สม่ำเสมอ)
5. **ถ้าเปิดไม่ขึ้นนานจนกระทบการขาย** — ขายด้วย POS offline ต่อ และเก็บบิลกระดาษสำรองไว้ แล้วติดต่อผู้ดูแลระบบพร้อมข้อความ error ที่เห็น
6. **เมื่อกลับมาแล้ว** — เปิด POS ค้างไว้จนคิวส่งหมด แล้วตรวจยอดขายวันนี้ในแอปเจ้าของให้ตรงกับบิลที่ขายจริง

ไฟล์สำรอง `menu-fallback.json` สร้างใหม่ด้วย `node tools/menu-fallback.mjs` ทุกครั้งที่แก้ `data/menu.csv` หรือข้อมูลร้านใน `supabase/seed_settings.sql` แล้ว build เว็บใหม่

## ลิมิตของแผนฟรี

อ้างจาก `data/free-tier.json` · เอกสารทางการ: https://supabase.com/docs/guides/platform/billing-on-supabase และ https://supabase.com/docs/guides/deployment/going-into-prod

| รายการ | ลิมิตแผนฟรี |
|---|---|
| ฐานข้อมูล | 500 MB |
| ผู้ใช้ที่ active ต่อเดือน (MAU) | 50,000 |
| พื้นที่เก็บไฟล์ (storage) | 1 GB |
| ข้อมูลขาออก (egress) | 5 GB |
| โปรเจกต์ถูก pause ได้เมื่อไม่ค่อยมีการใช้งาน | ภายใน 7 วัน |

ตรวจขนาดฐานข้อมูลเอง: `node tools/usage-check.mjs` → บอก `ปกติ` (exit 0) / `ใกล้เต็ม` เมื่อถึง 80% ของลิมิต / `เต็มแล้ว` เมื่อถึง 100% (ทั้งสองอย่างหลัง exit 1) · ควรรันสัปดาห์ละครั้ง
ในเครื่องมันวัดฐานในเครื่อง ส่วนฐานบน Cloud ให้ดูตัวเลข Database size ใน Dashboard → Usage **[ตรวจหลังสมัคร]** (storage, MAU และ egress ดูได้ที่หน้า Usage เท่านั้น เครื่องมือของเรายังไม่ได้ตรวจ)

## สำรองและกู้คืน

แผนฟรีไม่มี backup ให้ดาวน์โหลด ต้องสำรองเอง · รายละเอียดจากเอกสารทางการ: https://supabase.com/docs/guides/platform/backups

- **สำรอง:** `bash tools/backup.sh` → ได้ไฟล์ `backups/story-cafe-วันที่-เวลา.sql` (บรรทัดสุดท้ายที่พิมพ์คือที่อยู่ไฟล์) ไฟล์มีข้อมูลลูกค้า ห้ามส่งต่อ ห้ามเข้า git (`backups/` อยู่ใน `.gitignore`) เปลี่ยนโฟลเดอร์ได้ด้วย `CAFE_BACKUP_DIR`
- **พิสูจน์ว่ากู้ได้จริง:** `bash tools/restore-check.sh backups/ไฟล์.sql` → กู้ลงฐานชั่วคราวแล้วเทียบจำนวนแถวทุกตาราง `✓` = ตรง · `✗` = ไม่ตรง (ถ้าไฟล์สำรองเก่ากว่าข้อมูลที่เพิ่มเข้ามา จะ ✗ ที่ตารางนั้น เป็นเรื่องปกติ) · ฐานชั่วคราวถูกลบเสมอ
- **ความถี่ที่แนะนำ:** ทุกวันหลังปิดร้าน และก่อนแก้โครงฐานข้อมูลทุกครั้ง · เก็บสำเนาไว้นอกเครื่องร้าน (เช่น ไดรฟ์ส่วนตัวที่ล็อกรหัส) อย่างน้อยสัปดาห์ละครั้ง · ทดสอบกู้ด้วย `restore-check.sh` เดือนละครั้ง
- **ข้อจำกัด:** สคริปต์สำรองฐานในเครื่อง (container ของ `supabase start`) เท่านั้น สำรองฐาน Supabase Cloud ต้องใช้ connection string ของโปรเจกต์กับ `pg_dump` เอง และ **ไม่ต้องเอา connection string ใส่ในไฟล์ใด ๆ ที่ commit** **[ตรวจหลังสมัคร]** · การกู้ลงโปรเจกต์ Cloud จริงก็ยังไม่เคยทดสอบ **[ตรวจหลังสมัคร]** · ผู้ใช้ (auth.users) ไม่อยู่ในไฟล์สำรอง ผู้ใช้ต้องสมัครหรือสร้างใหม่ (ข้อมูล public ที่อ้างถึงผู้ใช้จะอ้างไม่ถึง)

## ถ้าข้อมูลหลุด

สงสัยว่ากุญแจหรือรหัสหลุด (เช่นเผลอส่งในแชท ขึ้น GitHub หรือเห็นรายการแปลกในระบบ) ทำตามลำดับ:

1. **ตัดกุญแจก่อน** — Supabase Dashboard → Project Settings → API Keys: สร้าง secret key ใหม่แล้วลบอันเก่า (ตัวที่ขึ้นต้น `sb_secret_` คือ service_role ห้ามอยู่ในเว็บหรือแอป) **[ตรวจหลังสมัคร]**
2. **เปลี่ยนรหัส** — รหัสผ่านฐานข้อมูล (Project Settings → Database) รหัสบัญชี Supabase/Cloudflare/GitHub และกุญแจของ Stripe กับ LINE ที่เกี่ยวข้อง (ยกเลิก key เก่าที่หน้าของผู้ให้บริการนั้น) **[ตรวจหลังสมัคร]**
3. **ใส่ค่าใหม่ผ่านตัวแปรสภาพแวดล้อม/ที่เก็บความลับ** ไม่ใส่ในไฟล์ที่ commit และไม่วางในแชท (`.env` ต้องไม่ถูก track)
4. **ถ้ากุญแจเคยขึ้น git** — การลบไฟล์ไม่พอ ถือว่ารั่วแล้ว ต้องหมุนกุญแจ (ข้อ 1) เสมอ
5. **ตรวจความเสียหาย** — รัน `rls_audit()` ด้วย service_role (ต้องได้ `[]`) ดูบิล/ออเดอร์แปลก ๆ แล้ว `bash tools/backup.sh` เก็บสถานะปัจจุบันไว้ก่อนแก้อะไรต่อ
6. **ลูกค้าได้รับผลกระทบหรือไม่** — ถ้าข้อมูลลูกค้า (ชื่อ เบอร์ ที่อยู่) อาจถูกเห็น ให้แจ้งลูกค้าที่เกี่ยวข้อง ปรึกษาผู้รู้เรื่อง PDPA ก่อนประกาศ
